# Internationalization direction

Status: supported-locale primitives, localized Darb public routes, per-business enabled/default
locale state, relational Restaurant content localization, and public Restaurant locale routing are
implemented.

## Initial market

| Setting           | Value            |
| ----------------- | ---------------- |
| Market            | Israel           |
| Currency          | ILS (`₪`)        |
| Platform timezone | `Asia/Jerusalem` |

The supported languages are:

| Locale | Language | Direction | Typeface |
| ------ | -------- | --------- | -------- |
| `ar`   | Arabic   | RTL       | Cairo    |
| `he`   | Hebrew   | RTL       | Heebo    |
| `en`   | English  | LTR       | Ubuntu   |

`@darb/i18n` owns the shared locale identifiers and direction primitives. It does not contain
business-specific translations.

## Darb public website

The platform-level Main website uses explicit `/ar`, `/he`, and `/en` routes. `/` permanently
redirects to `/ar`; automatic browser-language negotiation is deliberately avoided so public URLs
remain stable. Each locale is canonical to its own path, all three localized routes are linked with
`ar-IL`, `he-IL`, and `en-IL` alternates, and the root redirect is the `x-default` entry. Language
switching preserves the equivalent homepage context. Public copy is centralized inside `apps/main`
because it is Darb-owned product content, not tenant content.

## Business language state

`core.businesses.default_locale` remains the single canonical default. `core.business_locales`
stores the enabled set for that business. The database enforces these invariants:

- only `ar`, `he`, and `en` are accepted;
- a business has one to three enabled locales;
- its default is always enabled;
- changing the default and enabled set is atomic through `core.update_business_locales`;
- new and migrated businesses receive an enabled row for their existing default.

The `/b/[businessSlug]/languages` page exposes this state to authorized members and requires
`business.manage` for changes. Locale rows describe availability only; they are not a generic
translation store.

Restaurant customer-facing content uses domain-specific translation tables for menus, categories,
items, variants, modifier groups, and modifiers. Rows are unique per entity and locale, reference
the owning business locale, and may be changed only while that locale is enabled. For the public
Restaurant experience, the business default locale uses `/{businessSlug}` and other enabled locales
use `/{businessSlug}/{locale}`. Unknown or disabled route locales fail closed. Entity text resolves
requested locale, business default, then remaining enabled Darb locales in stable platform order.
Location selection is orthogonal and preserved across language links.

Public metadata emits only enabled locale alternates using `ar-IL`, `he-IL`, and `en-IL`. The
locale-less canonical default route is intentionally also `x-default`. Canonical, alternate,
sitemap, structured-data, and Open Graph URLs all use the same trusted
primary-custom-or-platform-origin decision. Mixed fallback entity text retains its source `lang`
and `dir` at the component boundary.

## Direction and layout

Applications must set valid `lang` and `dir` attributes at the document boundary. Components must
use logical CSS properties where possible and explicitly isolate mixed-direction text such as
addresses, telephone numbers, codes, and brand names. RTL support affects navigation order,
alignment, directional icons, transitions, and spatial assumptions—not just text alignment.

Keyboard behavior, screen-reader announcements, truncation, tables, forms, and responsive layouts
must be tested in both directions. Mirroring an icon is a semantic decision; icons such as media
controls or brand marks should not be mirrored automatically.

The theme resolver maps locale to the approved Cairo, Heebo, or Ubuntu family and emits the
matching direction. Template composition remains locale-agnostic: a template may not encode one
writing direction as its structure or accept tenant-supplied font-family values.

## Formatting and time

Dates, times, numbers, plural forms, and currency must use locale-aware platform APIs. Store and
transport unambiguous timestamps; render them with the correct business or platform timezone. Do
not concatenate translated fragments or assume that ILS formatting is identical across languages.

## Deferred decisions

- automatic locale negotiation and persistence beyond explicit Restaurant routes;
- URL locale strategy for engines beyond Restaurant;
- translation catalogue tooling and ownership;
- server/client message-loading boundaries;
- multilingual models for engines beyond Restaurant; retain domain-specific relational models and
  do not introduce a generic EAV translation table.

These decisions require product and SEO requirements. Platform administration remains English at
this phase; the public Restaurant renderer sets locale, direction, and approved font at the document
boundary.
